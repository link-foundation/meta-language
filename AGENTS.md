# Instructions for automated contributors

These rules apply to every automated agent (AI solver, bot or script) that
changes this repository. Human contributors follow them too; see
[CONTRIBUTING.md](CONTRIBUTING.md) for the development setup.

## The contract

- [`docs/vision.md`](docs/vision.md) is the authoritative vision and
  architecture specification. Read it before starting. Do not add a competing
  vision, roadmap or architecture description elsewhere. If the work changes the
  architecture, update `docs/vision.md` in the same pull request.
- Requirements come only from the sources registered in
  [`parity/issue-195-sources.json`](parity/issue-195-sources.json), with their
  content hashes. Before relying on the ledger, run
  `cd js && npm run check:issue-195:sources -- --online`. When it reports an
  edited or unregistered comment, re-read the comment, reconcile the ledger rows
  and then refresh the register with `--update`.
- Every obligation is an atomic row of
  [`parity/issue-195-requirements.json`](parity/issue-195-requirements.json),
  generated by `js/scripts/issue-195-requirements.mjs`. Add rows for new
  obligations. Never remove a row, an assertion, a fixture, a runtime or an
  alias, and never rewrite a row's source, expected behavior or scope.

## Evidence, not declarations

- A requirement passes only when tests executed on the exact commit recorded
  every declared assertion for every declared fixture. Record observations
  (`recordIssue195Observations` in JavaScript, `record` in Rust) only after the
  assertions hold.
- Do not add status, complete or completed fields, skipped cells, planned
  fixtures presented as evidence, or capability declarations presented as
  support.
- A red aggregate while work remains is the truthful status. Never weaken a gate,
  an oracle mapping or an acceptance definition to turn it green.
- Do not claim completion in documentation, changelogs, pull request
  descriptions or releases while any ledger row fails. Do not add an
  issue-closing directive until every requirement is verified and delivered.

## Code

- Both runtime packages (`js/` and `rust/`) implement every feature with the
  same observable behavior; update
  [`parity/language-features.json`](parity/language-features.json) with the
  change.
- Canonical concept names are unabbreviated English noun phrases, and operations
  are verb phrases (see
  [readable English names](docs/vision.md#readable-english-names)). A new
  canonical name needs a record in
  [`parity/naming/canonical-concepts.json`](parity/naming/canonical-concepts.json);
  `cd js && npm run check:naming` checks every record and source name against
  WordNet 3.1, the registered abbreviations and technical terms, and the
  positive and negative fixtures in
  [`parity/naming/naming-fixtures.json`](parity/naming/naming-fixtures.json).
- Keep experiments in `experiments/` and runnable demonstrations in `examples/`.
- Run the JavaScript checks (`cd js && npm test && npm run check`) and the Rust
  checks (`cargo fmt --check`, `cargo clippy --all-targets --all-features` and
  `cargo test --all-features` in `rust/`) before pushing. Add a changelog
  fragment under `rust/changelog.d/` for user-visible changes.
