# Represented Symbol registry draft

The protected Symbol namespace now links genuine `Symbol.for` / `Symbol.keyFor` callable identities to shared bytecode and heap operations. `Symbol.for` uses ordinary implicit ToString, including real object coercion callbacks and Symbol rejection. `Symbol.keyFor` accepts only a primitive Symbol, without unboxing or coercion. The normative inventory is [ECMAScript 2025 Symbol.for](https://262.ecma-international.org/16.0/#sec-symbol.for) and [Symbol.keyFor](https://262.ecma-international.org/16.0/#sec-symbol.keyfor), bound to Node 22.15–22.x / 24.x.

The additive heap directory is `symbolRegistryModel: 'represented global Symbol registry 1'` with ordered `symbolRegistry: [{ $: 'symbolRegistryEntry', identity, key }]`. Keys retain exact primitive UTF16; the order is not Unicode scalar order or normalization. Existing `symbolRegistrationFact` records gain optional `key` witnesses. Old Boolean-only facts remain valid. A registered key lacking its actual exact witness refuses `keyFor`; creating a new registry entry refuses unknown imported registration/key authority. Complete known witnesses may initialize the shared directory. Directory entries/classification/key witnesses are rechecked for ordering, uniqueness, global identity, consistency and resource bounds. Successful represented operations extend key/identity membership or reuse established pairs; canonical storage order is not exposed as registry iteration.

New modules are `javascript-symbol-registry.js` and `javascript-symbol-registry-call-source.js`. One `symbolRegistry` instruction dispatches lookup/allocation and keyFor. Registered allocation reuses the existing Symbol ID allocator with a retained exact registry key, so allocation has the same source continuation and global identity authority. The kernel never invokes native `Symbol.for`. Registered descriptions, explicit String conversion and computed method naming use the actual retained key metadata. Weak registered-key rejection follows the same shared classification facts.

The actual embedding uses protected native `Symbol.keyFor` only to import an external Symbol's key witness. An external registered Symbol binds an already represented matching key to the canonical semantic identity. Internally created registered Symbols intentionally receive no fabricated native registered handle; native materialization refuses until an actual external registered Symbol witness is imported. Internal source observations continue normally. This distinguishes boundary identity/materialization authority from registry contents and avoids a host registry implementation fallback.

Deferred controls include 30 independent positive source originals and two explicit frontiers in `js/tests/fixtures/javascript-symbol-registry-source.mjs`, exported as `javascriptSymbolRegistryOriginals`, `javascriptSymbolRegistryRefusals`, `javascriptSymbolRegistryAssertionPolicy` and `javascriptSymbolRegistrySourceVersions`. `translation-javascript-symbol-registry.test.js` compares actual source-machine results against native originals. It separately obtains registry owners from two independently created actual native realms, compiles their actual identities into one shared-heap program and compares canonical identity across those linked owners; native registry calls are independent oracle operations only. Missing old key authority, reentrant coercion, lone surrogates, keyFor noncoercion, registered weak rejection and external witness binding have controls.

The exact former `Symbol.for` weak-collection refusal input is preserved as a positive original, with the expected behavior corrected by the new genuine registry path. Weak fixture totals are now 34 positives / four frontiers. The retention tracer treats actual global registry Symbol entries as agent roots.
