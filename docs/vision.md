# Meta-language vision and architecture

This is the authoritative specification of what meta-language is for and how it
is built. Everything else in this repository serves it: where the root
[README](../README.md), a package README, the
[grammar subsystem documents](grammar/README.md), the
[parity roadmap](parity-roadmap.md), a case study or a code comment disagrees
with this document, this document is the contract and the other text is a
defect to fix.

This document describes the **target**. It does not claim that the target has
been reached. What is actually implemented and verified today is the generated
[requirement ledger](issue-195-requirement-ledger.md), computed from observed
test execution. The [current state](#current-state) section lists the largest
known gaps.

## One common language of links

Meta-language provides **one common, extensible language, represented
recursively as links and serialized in Links Notation**. It covers:

- language grammars and the concepts they define;
- complete concrete syntax trees, produced by default;
- optional abstract syntax trees that keep explicit provenance back to the
  concrete syntax;
- semantic representations: bindings, types, universes, effects, ownership,
  macros and notation, and proofs;
- the transformations and translations over all of the above.

A grammar, a parsed document, a semantic annotation and a transformation rule are
all links in one network. None of them lives in a side table, an opaque string
payload or a host-language callback that the network cannot inspect.

The goal is coverage of **all existing languages**. The popular languages,
dialects, grammar formats and downstream workloads named here and in the ledger
are mandatory minimum inventories, not a permanent shortlist.

Both runtime packages, the Rust crate `meta-language` and the npm package
`meta-language`, implement the same features with the same observable behavior.
[`parity/language-features.lino`](../parity/language-features.lino) enforces
this, and the runtime-parity rows of the ledger check it again on shared
fixtures.

### Global concept space

All grammars of all languages inhabit **one global concept space**. It includes
programming languages, grammar-description languages, document formats and
natural languages, together with the translation rules over their concepts.
An unshared concept belongs to this same space; it retains its own identity and
qualified language provenance until an equivalence proof permits reuse.

The automated translation and import pipeline first copies every concept and
its recursive links into this space without losing rules, aliases, occurrence
order or provenance. Deduplication then constructs a checked one-to-one
correspondence between the complete reachable definitions. The correspondence
must preserve recursive structure, operational context, semantic distinctions,
binding, effects and any proof assumptions. The certificate records the paired
concepts and the evidence used to validate every pair. Equal names, samples or
accepted text alone do not establish equivalence. An unsupported or ambiguous
proof leaves both identities intact and preserves the candidate correspondence
as data.

Every verified equivalent concept resolves to the same stable global identity
at every occurrence in every grammar and translation rule. Its original
language-specific spelling, concrete syntax and source location remain aliases
and provenance on those occurrences. Distinct integer, whitespace, binding,
effect and universe meanings retain distinct identities even when their names
coincide. The complete space and its certificates serialize as links, reload
without the original grammar sources and yield identical decisions in both
runtime packages. Shared identity simplifies translation by exposing a reusable
meaning; target-specific syntax and faithful encodings remain explicit rules.

### Recursive formal concept definitions

Every concept has a deep recursive formal definition made of inspectable links.
Definitions can use other concepts, including shared and mutually recursive
references; identities, bindings, axioms, selected primitives and foundational
assumptions remain explicit through serialization and reload. An English
description or a declared meaning signature complements that formal definition
and cannot substitute for it. Definition comparison checks obligations under
the declared model and preserves an unknown result when a proof is unavailable.
It does not promise to decide arbitrary program equivalence.

The current typed-program adapter serializes checked semantic records, ordered
containers, scalar values and explicit binding, declaration, datatype and
constructor references as links. Constructor identities belong to their actual
datatype; equal constructor names in different datatypes remain distinct.
Pattern bindings have inspectable name and type records, and each case retains
its own lexical scope, including shadowed names and ignored ordered slots.
Reload validates structural and semantic traversal limits, types, ownership,
constructor arity and match coverage before emission. The data, constructor and
match projections reuse the existing surface checker and compare the complete
rechecked semantic program. Shared decision data supplies reference roles,
operand traversal, projection instructions and role-specific absent fields.
These source-free semantic graphs emit canonical target syntax; byte-identical
unchanged-source preservation remains the separate lossless CST contract.
Integral metadata uses the value of its linked Number. The fixed type bit-width
role accepts equivalent finite spellings such as `32`, `32.0` and `3.2e1`,
including the same type inside an owned proof. Its supported widths still come
from the shared typed schema. Native decoding normalizes only that declared
role before reading its integer field; primitive floating values and all other
scalar roles keep their existing interpretations.
Direct native programs can retain dynamic proof widths as floating Number
values. Their selected validation uses a bounded private comparison view with
the same fixed-width record adapter as Links decoding; the original proof
values, own-field order, nulls and unknown fields remain observable and checked.
Owned occurrence paths likewise compare the numeric value of an actual Number

Equivalent integral spellings retain their stored scalar, including negative
zero naming position zero. String fields remain distinct from numeric array
positions, and fractional, out-of-range and unsafe positions are refused.

### Ontology and taxonomy entry points

The library exposes ontology and taxonomy as separate entry points into the
same concept space, including concepts no grammar currently uses. The ontology
organizes concepts, relationships and formal axioms; the taxonomy organizes
classification and explicitly declared subsumption. General associative relations
remain separate from classification edges. This terminology follows the
[W3C ontology overview](https://www.w3.org/TR/owl2-overview/) and
[SKOS distinction between hierarchical and associative links](https://www.w3.org/TR/skos-reference/#semantic-relations).

A concept can participate in either entry point or both without losing its
global identity or formal definition. Each view can have several independently
selectable roots, all represented explicitly as links. A root may also be a type
when the selected model declares that role; root membership does not imply a
type role or a universal `Type : Type` axiom.
The current paired view APIs retain actual concept, recursive definition and
provenance links, including explicit orphan concepts. Ontology and taxonomy roots
are independently selectable; associations, axioms, classification and subsumption
carry declared model links. These declarations preserve assumptions and do not
establish arbitrary hierarchy or type entailment.

### Links as fundamental entities and relationships

Concepts, entities, relationships, roots and definitions are all links or
compositions of links. The same link can occupy several of these roles without
becoming disconnected host objects. A vertex can be represented by a link whose
beginning and end refer to that same link; the self-reference and the chosen
model remain explicit. Recursive composition preserves shared references and
cycles across representation levels.

The user's fractal and wave analogy is captured verbatim in the hashed
conversation sources as modelling motivation and a hypothesis. Physical claims
about waves and particles, mathematical self-similarity and absence of logical
contradictions are not established by this representation or analogy. Any
consistency or semantic equivalence claim requires its own explicit assumptions
and checked proof.

## Links Notation fitness

Links Notation (LiNo) is the serialization of the common language. Both packages
depend on the current links-notation release. The npm and crates.io releases are
checked separately rather than assumed to be at the same version. Version-coupled
grammar fixtures are regenerated against the release, and the installed packages
are tested.

- arbitrary arity;
- shared, recursive and forward references;
- identity and ordering;
- indentation and nested multiline groups;
- quoting and escaping;
- comments and trivia;
- Unicode and exact source mappings.

cover:

- whitespace and runtime differences;
- indented identifiers;
- deep nesting;
- long quote runs;
- stack safety;
- nonlinear parsing.

Resource safeguards are explicit and tested. Nesting deeper than the official
64-level limit becomes an `ERROR` node, never a stack overflow. Parse cost is
guarded as linear in the input size. These safeguards are not disguised as
missing language support. If a required feature is missing from Links Notation,
meta-language implements the representation support, with tests, as part of the
delivery. An upstream ticket or a feature declaration alone does not count.

## Native merged grammars

The shipped canonical grammar of every language is a **native Links Notation
grammar**. It is synthesized by carefully merging every applicable inventoried
source: official grammars and specifications,
[ANTLR grammars-v4](https://github.com/antlr/grammars-v4), tree-sitter grammars

- copying a generated parser;
- wrapping an external engine;
- storing a foreign grammar as a string;
- renaming imported files.

Ordinary installed parsing works without any of these:

- external grammar engines;
- subprocesses;
- foreign generated parsers or scanners;
- downloads;
- caller registration.

Any generated acceleration derives reproducibly from the native Links Notation
definitions and does not conceal another authoritative grammar. Importers and
converters, described in
[grammar import, conversion and reverse conversion](#grammar-import-conversion-and-reverse-conversion),
are authoring and interoperability tools. Their final product is a full native
grammar that meta-language itself can inspect, transform, execute and emit.

The **native dependency boundary** is tested. The installed production packages
parse with every external grammar engine and oracle asset absent. Changing one
native linked grammar rule changes the output of the public parse path, without
an unrelated host-code patch.

Natural-language documents also use executable native Links grammars. Their
concrete representation retains Unicode lexemes, punctuation, whitespace,
sentence and document structure, exact source spans and rejected-control
diagnostics. Language-specific lexical and grammatical annotations extend that
tree with links and provenance. An uncertain analysis remains a set of explicit
alternatives; a segmentation tree or a finite starter lexicon does not establish
complete morphology, syntax or meaning for a language. Their concepts belong to
the same global space as programming languages, and reuse requires the same
checked meaning correspondence. Tests distinguish native representation and
source preservation from any richer linguistic capability they verify.

## Grammar feature union

Structured scanner descriptors cover whole-line quoted and FIFO here-documents,
nested quoted and interpolation contexts, offside layout tokens and Markdown
fence width and indentation rules. Shared accepted and rejected lexical fixtures
verify their concrete trees in both executors. These scanner checks do not
establish completion of a whole language grammar or its independent corpora.

Reusable scanner family descriptors generate executable Links Notation data
through `js/scripts/scanner-families.mjs`. Delimiter parameters cover nested
comments, escaped strings and content that stops at interpolation boundaries.
Both executors consume the generated operations in
`parity/fixtures/scanner-families.lino` and compare complete concrete trees,
including Unicode text and rejections of truncated delimiters.
Repeated delimiter counts use the same operation language. The raw-string and
long-bracket cases in `parity/fixtures/scanner-counted-delimiters.lino` verify
matching marker counts, shorter closing candidates inside content, Unicode
bytes and independent state for successive tokens in both executors.
The split counted-delimiter family retains the opening count across separate
opening, content and closing tokens. The generated Lua scanner uses it for
long strings and block comments, with empty content and NUL rejection, and
reproduces the pinned upstream scanner's eight-bit counts. The native Lua
grammar and its corpus inputs are pinned alongside the other source grammars;
CI compares both executors with their independent Lua oracles.
The delimiter-run family shares configurable quote-run content and closing
operations; the line-boundary family emits a zero-width boundary before a
newline or the end of input. TOML uses both families, and
`parity/fixtures/scanner-delimiter-runs.lino` checks several delimiter lengths
and line endings with both executors.
The generated TOML, Zig, Pascal and Visual Basic grammars record reviewed
precedence, overlapping-choice and field-variant reconciliations in the import
pipeline. Contextual rule variants keep original concrete kinds and concept
identities while isolating overlapping loop-prefix expressions; opaque operand
rules retain their ordinary expression context. Optional literal preferences
retain the absent branch and consume the pinned parser's field modifier.
Alias-pattern priorities distinguish explicit conditional directives from generic
preprocessor extras. Field-selected associativity preserves each source alternative
while reproducing reference-led chained comparisons. Error-union priorities retain
optional and pointer type prefixes around their complete operand.
Shared operand precedence now requires evidence from the actual first child or
its inspectable reduction. A literal prefix cannot inherit an operand position
from another production alternative. Thirteen pinned Rust controls preserve
complete CST rows and field roles, and the affected Formal AI source reproduces
all 7,321 oracle rows without changing its source grammar or census. This checks
the imported grammar's concrete structure; it does not establish the compiler's
semantic interpretation of an ambiguous CST operator.
The CSS, PowerShell and Erlang imports use shared marked-lookahead, contextual
token and line-counted delimiter scanner families. Contextual keyword exclusions
retain every source production and reserve initial statement keywords while
preserving command prefixes, pipeline tails and explicit invocations. The pinned
Erlang scanner license accompanies its source separately from the grammar license.
CI reads immutable pinned corpus inputs, including Zig compiler
source cases and Visual Basic project sources, and compares every input with
its independent oracle in both runtimes.

The indentation family generates zero width newline, indent and dedent tokens
with descriptor owned widths, bounded counts, comments, continuation and reset
characters. The shared `parity/fixtures/scanner-indentation.lino` examples check
independently specified nested block structures and exact source preservation.
The executor retains actual lexed continuations across intervening virtual
tokens when deciding whether a pending layout token preempts a longer parse.
The prefixed quoted family stores raw, bytes and interpolation flags with each
quote delimiter and its triple quote policy. Python uses the indentation and
prefixed quoted families in its generated native grammar; ordinary parsing
selects that grammar in both packages. Focused examples retain complete oracle
trees for nested formatted strings, escapes, layout and exception aliases.
The pinned upstream corpus remains a separate CI check; this implementation
does not yet constitute the required multi source union of Python grammars.

The template context family retains nested quoted, interpolation, directive
and here-document contexts, with closing labels on a separate text stack.
The generated HCL grammar uses that family in both packages; Tree-sitter HCL
is a development oracle. Scanner `matched` reads from the token start through
the current cursor, independently of a marked token end. Wrapping a scanner
token retains its skipped trivia outside the token span; zero-width layout
tokens keep their grammar-owned padding. The shared catalog also records
whether a language's root includes leading trivia, so HCL retains its input
start while its child nodes keep their actual token boundaries. HCL collection
comprehensions are distinct from imperative loop expressions. Focused fixtures
check nested templates, Unicode escapes, closing-line boundaries and label
reset; CI checks the pinned upstream corpus. This single pinned HCL source
does not yet constitute the required multi source grammar union.
The language catalog generator also derives Rust's embedded grammar table
from the shared inventory, so every declared native grammar is available to
ordinary parsing without a separate host registration.

The grammar representation and its executor cover the complete union of the
grammar features that the inventoried sources use:

- ordered and unordered alternatives;
- recursion, including left recursion;
- precedence and associativity;
- ambiguity and conflicts;
- lexical priority and longest-match rules;
- Unicode and byte classes;
- token boundaries and trivia;
- lexer modes, channels and state;
- indentation and layout;
- context-sensitive predicates;
- semantic actions and attributes;
- captures, fields and aliases;
- parameterization;
- imports and inheritance;
- macros and notation;
- embedded languages;
- error and missing nodes, and recovery.

External scanner behavior and action semantics become structured, executable
link definitions. They are not uninterpreted source blobs or hidden
language-specific callbacks.

The native importer lowers character-class intersection, difference and
symmetric difference to the existing Links lookahead and consuming operations.
Ranges and implicit union bind before set operations, which associate to the
left; outer negation binds last. Both packages execute the generated Links
data, with positive and negative ASCII and Unicode fixtures, and an independent
regular expression oracle in tests.
Hexadecimal scalar escapes with fixed widths or braces lower to literal
characters and ranges through the same importer.

Every unique concept and semantic distinction is preserved. Concepts are shared
only where a faithful one-to-one correspondence of meaning is established:
similar spelling, or accepting the same strings, is not enough. In particular
the representation distinguishes:

- ordered from unordered choice;
- lexical from syntactic precedence;
- different integer and overflow models;
- binding rules;
- effects;
- proof universes.

## Concrete and abstract syntax trees

Default parsing produces a **full lossless concrete syntax tree**. It records:

- node kinds;
- fields;
- hierarchy and order;
- exact tokens, trivia and source bytes;
- spans;
- error and missing nodes with their recovery;
- embedded-language boundaries.

A source envelope, or a root node above a list of tokens, is not a complete tree.
Optional abstract syntax trees keep explicit provenance back to the concrete
syntax. Trees can be:

- serialized and reloaded without the original source;
- constructed;
- edited;
- generated back to source;
- reparsed.

## Grammar import, conversion and reverse conversion

Both runtime packages provide public APIs and command-line tools to import,
validate, convert, merge, rename, export and round-trip grammars. The format
catalog starts with:

- BNF, EBNF and ABNF;
- PEG, Peggy and Pest;
- ANTLR;
- tree-sitter source and JSON;
- Lark;
- GBNF;
- Yacc/Bison;
- lexer specifications.

This list is a minimum and is reconciled with the other widely used formats.

The JavaScript Yacc/Lex draft lowers declared token rules, left and right
precedence, `%prec`, lexical modes, trivia and supported arithmetic or textual
actions to shared native Links operations. Rejection actions become explicit
failures. Unsupported prologues, arbitrary host actions, typed unions and other
unimplemented constructs retain precise diagnostics. These finite supported
cases do not establish complete source-format coverage, a Rust importer or the
union of the pinned official Ruby, Perl, Bash and OCaml grammars.

- Every feature of every inventoried format has an explicit native
  representation, an operational meaning and executable tests. Imports follow
  included grammars, supporting lexer and scanner definitions, and action code;
  importing only rule skeletons is incomplete. Grammar-level comments, source
  locations, original names and formatting provenance are preserved.
- Conversion runs **back** to every source format. The tested cycle is source
  grammar → native links → exported grammar → native links, with the original
  source unavailable to the emitter. It checks structural and semantic
  equivalence, modulo documented canonical names and reversible provenance
  mappings. A lossless mode additionally reconstructs the source exactly.
- Cross-format conversions and native → external → native cycles are tested
  alongside same-format cycles. Exported grammars run under the actual
  independent target tools, which compare:
  - accepted and rejected programs;
  - parse structure;
  - lexical decisions;
  - precedence;
  - actions;
  - diagnostics.
- Where a target notation is less expressive, the export is a faithful lowering
  or runtime encoding, with any reconstruction metadata kept explicitly. An
  executable target grammar is distinguished from a lossless interchange package.
  None of the following is proof of semantic preservation:
  - an opaque sidecar;
  - a silently dropped feature;
  - a syntactically valid file;
  - a finite membership sample.
- Round-trip tests change the grammar before export, so returning the saved input
  cannot pass. Malformed and negative cases stop two mutually wrong importers and
  exporters from validating each other.

## Automatic merging, concept recognition, deduplication and renaming

The default merge pipeline is non-interactive. It:

1. discovers and imports the inventoried sources;
2. recognizes corresponding concepts even when their names differ;
3. reconciles their definitions;
4. normalizes names;
5. deduplicates genuinely equivalent concepts and preserves unique ones;
6. emits the canonical native grammar together with a reproducible provenance
   and decision report.

Concatenating rules, prefixing every source namespace or asking users for every
correspondence does not satisfy this.

- **Renaming is binding-aware.** It runs through references, imports, captures,
  semantic actions, mappings and generated artifacts, and keeps stable
  identities and the original source aliases for export. Tests cover:
  - collisions;
  - shadowing;
  - recursive and mutually recursive rules;
  - qualified references;
  - references after serialization and reload.
- **Duplicates are recognized by meaning**:
  - meaning-aware normalization;
  - recursive graph and alpha-equivalence;
  - lexical and parser semantics;
  - justified equivalence mappings.

  Name similarity and generated examples only nominate candidates. Tests cover
  differently named equivalent concepts and identically named non-equivalent
  concepts.
- **Uncertain matches are not conflated.** Distinct meanings, and version,
  dialect or ambiguity alternatives, stay explicit. An unresolved required
  equivalence is failing work, not a request for maintainer feedback or a
  permanent manual mode. Finitely many samples never prove arbitrary semantic
  equivalence.
- **Shipped and test grammars are merge outputs.** Both the production grammars
  and the native grammars used in tests come out of the multi-source merge.
  Upstream oracles stay independent. Each compatible source keeps its unique
  valid coverage. Dialects are not united indiscriminately, and disagreements
  are not erased to improve a score.
- **Merging is deterministic.** Tests cover:
  - reproducible output and idempotence;
  - stability under input reordering;
  - incremental re-merging after upstream changes;
  - conflict resolution;
  - no duplicate canonical identities for established equivalences;
  - preserved language and edition boundaries.

  Explicit precedence between sources is a reproducible rule justified by
  language specifications and independent evidence.
- **"Best possible" is measured.** The order of importance is:
  1. construct coverage and correctness;
  2. preserved unique features and shared reuse;
  3. measured recovery quality, execution time and memory.

  Comparisons against the inventoried source grammars are published.
  Superiority is never claimed from passing the same self-generated fixtures.

## Readable English names

Canonical concepts are self-explanatory English **noun phrases**, and operations
and relations are **verb phrases**, with no abbreviations: "expression",
"statement", "function declaration" and "resolve reference", not "expr",
"stmt", "fn decl" and "resolve ref".

Every canonical concept has:

- a stable identity;
- a readable phrase;
- a meaning or definition;
- its applicable constraints;
- its source aliases.

Language-specific tokens, external identifiers and original names remain
lossless provenance and aliases. Source code is never translated, and round
trips are never broken, to enforce the convention.

Naming and renaming are built into import and merge. CI enforces:

- the vocabulary;
- the phrase role;
- abbreviation expansion;
- collision and duplicate checks;
- full inventory coverage.

Positive and negative fixtures include deliberately abbreviated, ambiguous and
duplicate names. A letters-only regular expression or a hand-picked example list
does not establish readability or semantic uniqueness.

## Four-language semantics and translation

JavaScript, Rust, Lean and Rocq have full representation and transformation, and
all **12 directed translations** work in both runtime packages through the common
editable links representation. The construct and project inventory includes:

- classes and objects;
- arrays and mutation;
- standard-library behavior;
- imports;
- higher-order functions;
- asynchronous behavior;
- ownership;
- macros and notation;
- types, universes and effects;
- proofs and tactics.

Normal JavaScript is accepted; users are not asked to rewrite it into an
annotated sublanguage. The contract of each version is in
[`docs/four-language-contracts.md`](four-language-contracts.md).

Translations preserve genuine semantic outcomes, including errors, aborts,
overflow and effects. Where a target has no native concept, the translation uses
a faithful operational encoding and runtime. Proof preservation is separate from
bounded testing. A theorem is carried as a faithful proof obligation in the
target and discharged there. A finite property check is never counted as a
general proof, and external kernel authority is never imported into RML. None of
the following is a substitute implementation; each is honest unfinished work:

- an unsupported-construct diagnostic;
- a claim that holds only for non-aborting executions;
- source pass-through;
- a bounded theorem check.

The current editable typed-program model represents immutable value products
with explicit ordered items, a frozen flag and an `immutable value product`
model. Fixed projections retain natural-number positions. Rust tuple source
admission preserves empty, singleton and nested arities; JavaScript admission
checks fresh dense `Object.freeze` arrays, actual element types, lexical origins,
parameter defaults and closed callers. A finite source dependency solver refuses
ungrounded cycles.
An uncalled product-returning function has no witnessed caller context and stays
unsupported. Existing homogeneous positional array annotations retain their
array representation. Mixed and nested scalar Copy positions require independent
product origins; ordinary reference-bearing tuples keep their existing array
model. Readonly module constants continue to require literal initializers.
Const bindings or declared types alone do not prove immutability, and arbitrary
arrays, identity observations, whole-product conditions, mutable aliases,
unknown escapes, sparse products and dynamic positions require additional
operational support.

Shared link rules validate these products during reload and compare the complete
rechecked semantic program before emission. Edits to the model, frozen flag,
arity, references or positions receive precise diagnostics. Scalar field
comparisons work under the selected scalar model; whole-product equality and
ordering remain unsupported until their source-language behavior has a faithful
encoding. Lean and Rocq preserve explicit product arities only under an accepted
product model. This bounded support does not establish the complete twelve-way
translation or project-wide semantics contract.

Parse → links → structured transform → emit or translate is one path. Along it,

- source-free snapshots and reloads;
- binding-safe edits and renames;
- project-wide elaboration with hygiene;
- source mappings;
- project changes.

## Temporary external grammar inputs

External grammar sources, generated foreign parsers, scanners and grammar
binaries are not stored in the repository. A tool downloads them temporarily
when imports, builds or independent oracle checks need them. Every directory
holding those inputs is ignored by Git. Tracked metadata retains immutable
versions, provenance, checksums, licenses and reproducible patch instructions;
downloads verify those checksums before use. Repository-native generated Links
Notation grammars remain the prepared meta-language snapshot.

CI provisions required inputs before checks and artifact construction. Temporary
compiled fallback assets can still accompany an installed artifact while the
existing production parser dependency remains, so clean offline consumers keep
their required behavior. This does not deliver the separate requirement to
remove every external production parser. Removing stored upstream assets must
preserve all language coverage, fixture identities, assertions and oracle
comparisons.

## Dependencies

Every retained runtime, development, build and optional dependency is inventoried
and kept at the current stable release as of the recorded audit date

- lockfiles and transitive resolutions;
- vendored grammar assets;
- generators;
- toolchains;
- workflow actions;
- pinned build images;
- published artifact contents.

gate also queries the registries again, and it fails when the recorded audit no

request.

## What finite tests establish

Tests establish behavior on the inputs they execute: the pinned corpora, the
generated cases with their recorded seeds, and the real projects. From those
executions they support, but do not prove, general claims:

- A passing round trip on a corpus shows the round trip on that corpus.
- Agreement with independent oracles shows agreement where the oracles were run.
- A property test bounds the probability of an undetected counterexample in its
  input distribution.

Universal claims, such as the preservation of a universally quantified theorem
under translation or the semantic equivalence of two grammars, need proofs or
decision procedures and are reported separately from test evidence. This
document and the ledger never present a finite sample as a universal result.

## JavaScript first and self-translation

Every feature is developed and debugged in JavaScript first, where builds and
test runs are cheap. Only a feature that is complete and green in JavaScript is
ported to Rust, in one batch, and the Rust version must then behave exactly the
same. A fix is not mirrored into Rust commit by commit.

The port is done by meta-language itself. A self-translation tool, a library
API and a CLI command in both packages, reads JavaScript or TypeScript into
meta-language links and writes Rust, and reads Rust and writes JavaScript or
TypeScript. Code it cannot translate yet is a gap in the translator, not
something to write by hand. Meta-language's own source is its main acceptance
corpus:

- JavaScript → links → JavaScript and Rust → links → Rust are byte-identical;
- JavaScript → Rust → JavaScript and Rust → JavaScript → Rust preserve
  behavior;
- comments, layout and names survive through provenance wherever the target
  can express them;
- as in
  [relative-meta-logic PR #184](https://github.com/link-foundation/relative-meta-logic/pull/184),
  every translated module has shared corpus cases whose expected outputs are
  written in Links Notation and checked in both runtimes;
- `parity/language-features.lino` lists every public JavaScript feature, and a
  test fails when Rust lacks one or the two produce different output.

[Self-translation](self-translation.md) describes the tool, its output format,
the round trips, the shared corpus and the per-module report against the
hand-written Rust.

The portable frontend tokenizes JavaScript regular expression bodies as whole
literals, including escaped delimiters and character classes, before reporting
unsupported regular expression semantics. Lexical boundaries and division
disambiguation use shared JavaScript decisions translated into Rust; lexical
recognition alone does not establish executable regular expression support.
Control-statement parentheses retain their lexical context through nested
expressions and comments, while qualified method calls retain value-expression
context. Each tokenizer lazily encodes its source once and reuses the encoding
across regular-expression literals, with absolute UTF-16 token offsets.
Template substitutions reuse these lexical decisions and the same encoding:
braces inside strings, comments, regex bodies and nested templates cannot end
a substitution. String and template escapes use the shared scalar decoder;
template cooking preserves line continuations and normalizes line endings.

TypeScript compile-time erasure selects native concrete-tree spans through
shared linked erasure definitions. Its source annotations and type-only
declarations remain provenance, including when no executable definitions remain.
Enums, namespaces and parameter properties retain carried obligations until
their runtime behavior has faithful linked lowering. Projection probes strip
restoration provenance before replay; source restoration alone cannot prove
semantic preservation. Native execution of the translated Rust remains a CI
verification boundary.

Everything is extensible with decorators: one decorator API for the importer,
grammar rules, merge decisions, concept mappings, the executor and recovery,
CST → AST, transformations, emitters and translation rules. Decorators compose
in a defined order and are stored as links data that both packages share.
They also make translated output match the existing hand-written source.

Grammar work runs in bulk through the automated pipeline: import, merging and
transformation of every catalog language in one batch, adjustments recorded as
data-driven rules, never hand edits of generated grammars. Tree-sitter is only
a test oracle. Changes are drafted and debugged as a batch and pushed once;
nobody waits idle on CI.

The pinned Groovy grammar runs through this same native pipeline, with its
original parser confined to independent test oracles. Reviewed source rules
reconcile literal end sentinels with the actual input boundary, prefer complete
expressions at a context boundary, and require an argument value before
preferring an optional call attachment. These decisions retain the original
productions and generate shared executable Links Notation for both runtimes.
Context guards and preferred copies retain the source lexer token identities;
they do not create duplicate source token occurrences. Field-local ordering,
contextual keyword spellings and newline runs keep their decisions in grammar
data, with input-boundary lookahead that skips extras and emits no CST leaf.
The C++ and SQL imports use remembered-content and remembered-literal scanner
families. Grammar-owned raw-string punctuation surrounds an exactly matched
opening label; a whole dollar-quoted literal composes opening, content and
closing rules. SQL function bodies retain their separate surrounding grammar
and prevent a closing function label from starting an inner literal. Every
catalog SQL dialect has its own default-source expectation for the shared
grammar. Named choice aliases retain a complete boundary and the selected
production beneath it. Contextual clause exclusions preserve quoted identifiers
and longer words. A named NULL marker keeps absent-literal recovery visible.
Pattern-guarded context preferences retain their original fallback choices.
C++ scoped calls and assignments, dependent type segments and array allocation
dimensions are reconciled through these grammar rules and field preferences.
SQL pattern keywords keep named token identities while excluding identifier
continuations; a complete IS NOT operator retains its own concrete kind.
Dart, Nix and CMake scanner policies are generated through the shared fragment,
lexical token, nested delimiter and counted delimiter families. Fragments retain
paired-prefix parity, reject configured invalid boundaries and can require a
marker. Delimiter opening lookahead distinguishes documentation comments without
consuming a closing star. Lexical external rules retain following context, and
counted content records explicit whitespace and end policies. Scanner-only token
renames retain their original concrete kinds. A source variable or bracket opening
commits to its complete production before overlapping literal text can fall back;
case-insensitive command keywords retain word continuation boundaries. Adjacent
Nix path fragments continue one path, while whitespace separates applications.
These policies are grammar data executed identically by both runtimes. Dart and
Nix parser crates and the separate vendored CMake oracle crate are development
dependencies. The published runtime uses the generated native grammar text.
Required concept distinctions are shared data in
`parity/required-concept-distinctions.lino`; the record generator emits the
JavaScript JSON and Rust constant data from the same pairs and reasons. SQL
unknown values and Pascal null pointers keep separate concept identities.
Remembered textual delimiters use grammar actions to store opening tags and
predicates to compare closing tags exactly. The generated content scanner
preserves other tags inside the body and supports successive distinct tags
through the same shared state model.

## Continuous integration

CI follows the same order as development. One workflow
([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)) runs the
JavaScript workflow first and the Rust workflow after it: no Rust job starts
before every JavaScript job passed, and the Rust jobs show as skipped when
JavaScript fails. Inside the acceptance workflow, the Rust evidence stages,
the Rust native translations and the Rust consumers likewise need the
JavaScript stages.
Registered native experiment inputs and shared Links data also activate the
Cargo lockfile, check and test prerequisite chain on pull requests. This
selection derives from the same native path filter and passes an explicit
Boolean to the called workflow. It preserves ordinary experiment and
documentation exclusions, the changelog policy and every earlier activation
condition; an unknown comparison base selects checks conservatively. A
JavaScript failure still prevents the Rust workflow from starting.

JavaScript evidence runs in separate group and shard jobs. Each physical
partition records its exact commit, selected test files, observations and logs
under a distinct identity. The aggregate requires every declared partition and
the complete test-file union before accepting the logical JavaScript suite;
missing, duplicate, mixed or foreign scope remains a gate error. The current
15 partitions cover all file groups within the existing 60-minute job limit.
Fourteen partitions run beside downstream workload producers; the downstream
partition retains its report dependencies. Both JavaScript collections must
succeed before Rust evidence starts, and both remain dependencies of the
aggregate with their original physical scope and artifact identities.
The Rust evidence suite starts only after the entire JavaScript matrix passes.
Its default-feature Cargo command retains every test target, the lockfile and
`--no-fail-fast`. It reuses the fresh-merge command's package-specific test
optimization with debug assertions and overflow checks explicitly enabled;
no release profile, feature selection or test filter replaces the suite.
Both suites provision their required formatter and compiler tools. Failure
tails and periodic command progress are retained in live CI output. Each
thirty-second heartbeat includes a bounded, credential-redacted actual log
suffix, so a job timeout retains recent test progress even if artifact upload
cannot run. Original command logs remain unchanged.

Package validation runs nine required logical check groups across ten parallel
jobs: native imports, native fixtures, grammar, contracts, generated code and
source models, complete original-link tables, binary candidates and raw graph
preflight. The
generated group has two physical slices. One retains the
literal-edit rule, fixture and experiment triplet; the other retains every
remaining generated check, including both compiler-feedback producers and their
single upload. All checks execute exactly once in their original relative order;
each runner keeps the same setup and ten-minute deadline. Distinct concurrency
identities prevent sibling cancellation. All six earlier check-context names
remain, and the additional generated slice has its own name. The
source-model group executes the new raw-binding and complete text-certificate
checks, isolated owned-certificate adapters, original-identity and role
projection checks, complete String-symbol and eleven-table projection checks,
fresh collector certificates and library packaging generators
without adding work to the original generated-code group. Two additional matrix
cells own the complete seventeen-table projection and binary metadata candidate
checks. They retain the same setup, cleanup and ten-minute deadline. Their
native runner contracts execute with actual compilation disabled; separate
required Rust steps compile and execute the complete artifacts only after the
JavaScript workflow passes. The new cells preserve the original six matrix
groups, seven physical cells and check-context names. The final package job requires
every group, every JavaScript test partition and the complete report assertion
job before packaging or publication. It also requires the validated merge of
translation compiler feedback. Frozen step-conservation checks retain every
original command, condition and artifact owner exactly once across the groups.
The raw graph cell separately checks the complete automatic native generation,
the serial JavaScript graph contracts and the CI-only injected native oracle.
Its checks use a one-GiB heap bound and retain the existing ten-minute deadline.
Its actual native oracle is a separate parallel Rust job with the complete
existing Cargo test prerequisites and admission condition. It preserves the
fifteen-minute Ubuntu test deadline, requires a SHA-qualified observation
artifact and adds no work to the nine existing native oracles. Removing
only this cell, its three steps and the new job restores the previous workflows
byte for byte; the global JavaScript-first caller and path selector are unchanged.

The JavaScript package checks also compile the generated shared frontend rules
as a standalone Rust module with the crate's Clippy lint groups and warnings
denied. This checks the generated interface without building the crate's
dependencies. Compiler style fixes remain decorator data applied to a fixed
point by the generator.

Every job reports all of its failures in one run, not only the first: `cargo
test` runs with `--no-fail-fast`, every check step after the first runs unless
the run was cancelled, and `cargo fmt`, clippy and `cargo doc` are independent
steps. A repository test checks this structure.

The self-translation report jobs publish generic and decorated measurements
for every JavaScript source module, with the commit and hashes of both runtime
sources. Both acceptance suites verify the complete published reports before
recording the per-module difference assertion; a small local report test alone
cannot supply that evidence.
Report import resolution checks every candidate callable and avoids resolving
dependencies of classes and forwarded names that the current source binder
cannot bind. Every source module still receives its complete measurement and
byte-coverage check.
Import and export candidate discovery uses the shared lexer, retaining opaque
literals and nested scopes. Unsupported lexical identifiers or syntax use the
original grammar scan. Every candidate signature still requires checked
translation; this optimization cannot supply an unchecked signature.
In CI one JavaScript worker measures a module while the coordinator resolves
the following module's imports. Contexts and results travel as LiNo records;
completed rows retain their original order. Local reports remain sequential,
and CI keeps the same report deadlines and verification gates.

The initial translation, native grammar and conformance test groups run in disjoint CI file
partitions. Their union retains every original file exactly once, and each job
keeps the existing time limit. File partitioning does not change assertions,
fixtures, runtime obligations or the requirement scope.
Three initial translation partitions retain the fifteen-minute deadline. Each
transports feedback with a LiNo receipt of the exact commit, selected files and
payload hashes. A required merge validates every partition, permits an empty
individual partition, rejects missing, stale or conflicting inputs, and restores
the original combined artifact name, paths and retention. An empty complete
collection still fails. Acceptance retains its separate fifteen physical scopes.

A separate JavaScript test group checks these published reports after all
report shards finish. It uses the producers' exact checkout and source hashes,
reuses their measurements, and must pass before Rust or delivery stages start.
Standalone JavaScript workflow runs produce and check their own report shards.

Real target-tool interchange reports identify the emitted target format, its
tool and version, the accepted and rejected corpus inputs and any failed cycle.
A Peggy report verifies the Peggy target only; it cannot satisfy the obligation
to execute cycles under every other real grammar tool. Development oracle
corrections build in CI and keep their original source hashes and a separately
identified correction, so the native runtime remains independent of the oracle.

## Resource limits

Local sandboxes and CI runners have a few gigabytes of memory. The tooling
keeps every run within that bound instead of relying on a larger machine.

Use one shared repository checkout for ordinary development, review and bounded
JavaScript checks, with explicit ownership of edited paths. Do not create a
worktree or clone for each agent, test or review. The coordinator may select an
isolated task worktree when the task requires it; share the existing dependency
installation rather than duplicating it. After its commits are preserved on a
named branch or integrated and no process or active task uses it, release that
task-owned worktree promptly with `git worktree remove` without `--force`.
Before removal, verify tracked and untracked changes and inspect ignored
contents for retained evidence or unique work. Preserve dirty worktrees,
evidence, active tasks and unrelated directories. A cache-cleanup run does not
release sibling worktrees. Cleanup is restricted to meta-language-owned storage;
it never clears unrelated project or user data. Rust compilation runs only in
CI/CD. Local Rust checks are limited to formatting changed files.

- CI runs a fast `cargo check` of all targets and features first; the jobs that
  compile and test need it, so a compile error fails once.
- CI splits the Rust tests by test target and filter, and the JavaScript tests
  by file group, into matrix jobs with their own timeouts. Every JavaScript test
  file still runs exactly once. Native grammar corpora, recovery and scaling
  checks have separate parallel groups with unchanged assertions and limits.
  Full C#, Elixir and Ruby candidate corpora run in separate JavaScript jobs
  with the same time and memory limits, keeping every corpus input and assertion
  while preventing their combined work from cancelling the general grammar job.
- The issue #195 evidence runs as separate stage jobs: the JavaScript suite,
  the Rust suite, runtime parity, each native translation target and delivery.
  The merge-enforcement report runs as its own post-merge job on `main`. Each
  stage uploads its own evidence. The Full Requirements
  Aggregate only merges and evaluates the stage outputs, and a failed or
  missing stage is one gate error naming it.
- Every workflow cancels the runs a newer push supersedes.
- Generated Rust compilation and style checks retain raw compiler diagnostics
  alongside the exact generated source and its hash as CI artifacts. Offline
  feedback applies only explicit machine-applicable suggestions against those
  unchanged sources. Rendered suggestions require a reviewed correction and
  cannot acquire invented applicability metadata.
  Multipart suggestions remain atomic, and replay retains the owning function
  signature so identical expressions in owned and borrowed contexts cannot
  receive each other's corrections. Reviewed collision repairs retain their
  provenance separately from authentic machine-applicable diagnostics.
- Full acceptance and native evidence stages execute in CI. Local validation
  remains limited to targeted JavaScript checks and changed-file formatting
  allowed by `AGENTS.md`. CI bounds compiler jobs and test threads with
  `CARGO_BUILD_JOBS=2`, `RUST_TEST_THREADS=2` and `CARGO_INCREMENTAL=0`.
- The JavaScript package loads each WebAssembly grammar on first use, compiles
  grammar code with a tiering budget so an idle process does not keep
  recompiling it, reuses one Markdown inline parser for every inline region,
  and maps source offsets through interval checkpoints instead of an entry per
  character.
- The runtime parity check streams the Rust observation as NDJSON, compares
  the runtimes entry by entry, and keeps one digest per entry plus the full
  entries only where the runtimes differ.
- Bounded-heap and peak-RSS tests in `js/tests/issue-195-evidence-memory.test.js`
  cover lazy grammar loading, Markdown inline parser reuse, multi-megabyte
  Unicode offset maps and parity artifacts larger than the heap. Artifact
  writing awaits each record instead of constructing the entire NDJSON string.
  `js/tests/issue-195-parse-memory-budget.test.js` retains the formal-ai
  regression: native TypeScript parsing accumulated memo cells until heap
  exhaustion; the shared parse budget now returns a diagnostic before that.
  Rule memo cells remain counted across runs and repair rounds. Optional fixed
  lexical caches count their retained entries against that same limit, and
  discard those entries when required parser work needs the space. Only the
  discarded cache cells are released; required rule work still rejects with
  `memoryBudget` when it exceeds the unchanged limit.
- A native validation stage deletes the compiler outputs no verification cell
  cites.
- `AGENTS.md` and `CONTRIBUTING.md` tell agents and contributors to run only

  leave the full acceptance pipeline, the native toolchain matrix,

## Packages and publication

The delivered capabilities reach users through matching, usable npm and
crates.io releases. Clean-consumer evidence covers both published packages,
relative-meta-logic and formal-ai. Candidate builds, or a publication workflow
that has not run, do not prove that users can install the delivered
capabilities.

Release publication verifies the release tag, checked-out commit, package
versions and lockfiles before either registry write. A registry preflight fails
closed when existing publication state cannot be established. The release then
checks that npm and crates.io expose the same intended version and verifies its
self-translation API through installed consumers. Trusted-publisher settings
and the release-tag workflow are documented alongside the publishing machinery.

## Current state

This section is a summary and may lag behind. The generated
[ledger](issue-195-requirement-ledger.md) is authoritative. The largest known
gaps against the target above:

- **Remaining external parsers and native coverage.** Generated native grammars
  now serve many catalog languages. Remaining production parsers, scanner
  families, document formats and grammar-description languages still need their
  complete native implementations and independent corpus evidence before the
  production dependency count can reach zero.
- **Incomplete source unions.** A native single-source import is insufficient.
  Every catalog language still needs the union of its applicable pinned official
  and mature grammar sources, with reproducible decisions and independent
  comparisons. Global concept sharing additionally needs checked semantic
  correspondences; structural similarity alone does not discharge that proof.
- **Grammar interchange.** Import and export capabilities do not establish the
  complete union of format features or cycles under every real target tool.
- **Four-language translation and self-translation.** Portable constructs are
  implemented, while complete real-project construct inventories, zero carried
  items, generated runtime replacements, faithful abort and effect encodings
  and proof preservation remain acceptance obligations.
- **Matching published releases.** The crate release and npm publication must
  expose matching versions and the delivered APIs. Exact published consumers,
  downstream integrations and post-merge rules still require executed evidence.
- **Full unsigned 64-bit identifiers in JavaScript.** The current public Number
  profile admits only exact positive safe integers. Primitive, text, writer and
  substitution boundaries reject imprecise identifiers before conversion;
  rejected insertions preserve the allocator and graph, and exhausted allocation
  refuses without replacing an existing link. Original decimal spellings and
  safe BigInt inputs normalize to the existing Number representation. An existing
  LinkId must retain its own Number data field; inherited values and accessors
  refuse before a getter can change the identifier between validation and use.
  Carrying
  the entire native unsigned 64-bit domain needs a broader exact representation
  and a separately versioned binary profile; that support is not established.
  Actual native endpoint capture also needs checked identifier exhaustion: the
  current native text importer and allocator still increment identifiers without
  a checked transition at `u64::MAX`. Synthetic word-vector checks establish
  neither an actual maximum-identifier graph import nor allocator safety.
